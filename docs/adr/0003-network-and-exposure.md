# 0003. 태스크를 퍼블릭 서브넷에 두고 노출 범위는 CIDR 로 좁힌다

- 상태: 승인
- 날짜: 2026-08-24

## 배경

Fargate 태스크는 ECR(이미지 풀), Bedrock, CloudWatch Logs, DynamoDB 로 아웃바운드
연결이 필요하다. 조직 기본 방침은 "VPC 가 필요한 리소스는 프라이빗 서브넷 + VPC
엔드포인트를 우선 검토" 다.

동시에 이 프로젝트에는 상충하는 제약이 있었다.

1. **비용.** dev·데모 환경을 상시 켜 둘 수 있어야 한다. 유휴 비용이 크면 목적을
   달성하지 못한다.
2. **원커맨드 설치의 신뢰성.** 구성 요소가 늘면 첫 배포 실패 확률이 올라간다.
3. **인터넷 노출 통제.** 사용자가 `0.0.0.0/0` 개방을 명시적으로 금지했고, 접근 대상
   IP 를 파라미터로 받아야 한다고 요구했다.

## 결정

**전용 VPC 에 퍼블릭 서브넷 2개만 만들고, 태스크에 공인 IP 를 붙인다.**
NAT Gateway 와 인터페이스 엔드포인트를 쓰지 않는다.

노출 통제는 세 겹으로 한다.

1. **ALB 보안 그룹**: 지정된 CIDR 1~3개에서만 80(있으면 443) 인바운드 허용.
   CloudFormation 파라미터 정규식이 첫 옥텟 `0` 과 모든 `/0` 프리픽스를 거부한다.
   배포 스크립트도 같은 검사를 먼저 수행해 오류 메시지를 명확하게 만든다.
2. **태스크 보안 그룹**: 인바운드는 **ALB 보안 그룹에서만** 8080 허용. 공인 IP 가
   붙어 있어도 인터넷에서 컨테이너 포트로 직접 접근할 수 없다.
3. **아웃바운드 제한**: 태스크는 443(AWS 엔드포인트)과 VPC 리졸버 DNS(53)만 나간다.
   ALB 아웃바운드는 VPC 내부 8080 으로만 제한한다.

비용이 없는 **S3·DynamoDB 게이트웨이 엔드포인트**는 붙인다. DynamoDB 트래픽과
ECR 이미지 레이어(S3에 저장된다)가 인터넷을 거치지 않는다.

## 검토한 대안

### 프라이빗 서브넷 + NAT Gateway — 탈락 (비용)

가장 표준적인 구성이고 먼저 검토했다.

- NAT Gateway 시간당 요금이 약 $0.045 이고 AZ 당 하나를 두면 월 약 $65, 하나만
  두면 월 약 $33 다. 여기에 데이터 처리 요금($0.045/GB)이 더해진다.
- 기본 구성 총액이 월 $37 인 상황에서 NAT 하나가 전체를 두 배로 만든다.
- AZ 하나에만 두면 그 AZ 장애 시 다른 AZ 태스크의 아웃바운드가 끊긴다. 가용성을
  위해 둘을 두면 비용이 더 커진다.

### 프라이빗 서브넷 + 인터페이스 엔드포인트 — 탈락 (비용, 복잡도)

NAT 없이 프라이빗 서브넷을 쓰려면 필요한 서비스마다 인터페이스 엔드포인트가
필요하다.

| 엔드포인트 | 필요 이유 |
|---|---|
| `ecr.api`, `ecr.dkr` | 이미지 풀 |
| `logs` | CloudWatch Logs |
| `bedrock-runtime` | LLM 호출 |
| `bedrock` | 모델 목록 조회 |
| `secretsmanager` | 관리 토큰 |

엔드포인트당 AZ 당 시간 요금이 약 $0.01 다. 6개 × 2 AZ 면 월 약 $88 이다.
데이터 처리 요금도 별도다. NAT 보다 더 비싸다.

AZ 하나로 줄이면 약 $44 지만 가용성을 잃고, 여전히 기본 구성 총액에 맞먹는다.

### 퍼블릭 서브넷 + 공인 IP 없이 — 불가능

퍼블릭 서브넷에 두면서 공인 IP 를 주지 않으면 아웃바운드 경로가 없다. IGW 는
공인 IP 가 있는 ENI 만 라우팅한다.

### ALB 없이 함수 URL / 직접 노출 — 탈락

CIDR 기반 접근 제한을 보안 그룹으로 걸 수 없다. WAF 나 애플리케이션 레이어에서
IP 를 검사하는 방식은 더 복잡하고 우회 여지가 크다.

## 결과

**얻는 것**

- NAT 대비 월 약 $33~65, 인터페이스 엔드포인트 대비 월 약 $44~88 를 절감한다.
- 구성 요소가 적어 첫 배포 실패 지점이 줄어든다. 원커맨드 설치 목표에 부합한다.
- 두 AZ 모두 독립적으로 아웃바운드가 가능하다. 단일 NAT 구성보다 이 점은 낫다.
- DynamoDB·S3 트래픽은 게이트웨이 엔드포인트로 VPC 를 벗어나지 않는다. 추가 비용
  없이 얻는 이점이다.

**잃는 것**

- **태스크에 공인 IP 가 붙는다.** 보안 그룹이 ALB 만 허용하므로 실질적인 접근
  경로는 없지만, 보안 그룹 설정 실수 한 번이 곧 인터넷 노출이 된다. 프라이빗
  서브넷이라면 실수의 영향이 한 단계 더 막혀 있다. 이것이 이 결정의 핵심 트레이드
  오프다.
- **아웃바운드가 인터넷을 경유한다.** Bedrock·ECR·Logs 트래픽이 AWS 백본으로
  가지만 공인 엔드포인트를 향한다. 규제 요건상 트래픽이 VPC 를 벗어나면 안 되는
  환경에서는 쓸 수 없다.
- 아웃바운드 443 을 특정 CIDR 로 좁힐 수 없다. AWS 리전 엔드포인트가 공인 IP
  대역이기 때문이다. 프리픽스 리스트로 좁히는 방법이 있으나 서비스마다 관리
  대상이 늘어 채택하지 않았다.

**새로 생기는 운영 부담**

- 접근 CIDR 이 바뀔 때마다 재배포가 필요하다. 재택 근무처럼 IP 가 유동적인
  환경에서는 번거롭다. 런북에 CIDR 추가 절차를 적어 두었다.
- 보안 그룹 규칙을 손으로 고치면 다음 배포에서 되돌아간다. 변경은 항상 파라미터로
  한다.

**비용 영향**

게이트웨이 엔드포인트는 무료다. 이 결정으로 추가되는 비용은 없고, 대안 대비 월
$33~88 를 절감한다.

## 프로덕션 전환 시 변경 사항

규제 요건이 있거나 노출 위험을 더 낮춰야 하면 다음을 적용한다.

1. `infra/app.yaml` 에 프라이빗 서브넷 2개와 NAT Gateway 를 추가한다.
2. ECS 서비스의 `AssignPublicIp` 를 `DISABLED` 로 바꾸고 서브넷을 프라이빗으로
   교체한다.
3. 비용을 더 줄이려면 NAT 대신 인터페이스 엔드포인트 6개를 붙인다. 트래픽량에
   따라 어느 쪽이 싼지 달라지므로 실측 후 결정한다.
4. ACM 인증서를 발급해 `--certificate-arn` 으로 HTTPS 를 켠다. 이건 프로덕션에서
   **필수**다. 인증서가 없으면 API 키가 평문으로 전송된다.

절차는 `docs/runbook.md` 의 "프로덕션 전환 체크리스트" 에 정리해 두었다.
