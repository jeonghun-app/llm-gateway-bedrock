# 0004. 기본 리전을 us-east-1 로 하고 분산 트레이싱은 v1 에서 제외한다

- 상태: 승인
- 날짜: 2026-08-24

이 문서는 서로 독립적인 두 결정을 담는다. 둘 다 조직 기본 방침에서 벗어나는
선택이라 근거를 명시적으로 남긴다.

---

## 결정 1: 기본 리전을 `us-east-1` 로 한다

### 배경

조직 기본 방침은 리전이 지정되지 않았으면 `ap-northeast-2`(서울)를 가정하는
것이다. 그런데 이 프로젝트에서는 두 가지 사실이 확인됐다.

- **빌드 호스트가 `us-east-1` 에 있다.** 배포를 실행하는 EC2 인스턴스가
  `us-east-1a` 에 위치한다.
- **Bedrock 모델 가용성 차이가 크다.** 확인 시점에 `us-east-1` 은 온디맨드 텍스트
  모델이 121개, `ap-northeast-2` 는 그보다 적었다. 또한 최신 Anthropic 모델은
  크로스리전 추론 프로파일(`us.` 접두어)로만 온디맨드 호출을 받는 경우가 있고,
  이 프로파일은 `us` 리전 그룹에서 동작한다.

### 결정

기본 리전을 `us-east-1` 로 한다. `--region` 옵션과 `AWS_REGION` 환경변수로
변경할 수 있고, Bedrock 호출 리전은 `LLMGW_BEDROCK_REGION` 으로 분리할 수 있다.

### 검토한 대안

**`ap-northeast-2`(서울) 기본** — 조직 방침이지만 이 프로젝트에서는 탈락.

- 빌드 호스트가 `us-east-1` 에 있어 ECR 푸시가 크로스리전이 된다. 200MB 이미지를
  매 배포마다 리전 간 전송하면 지연과 데이터 전송 비용이 발생한다.
- 사용 가능한 모델이 적다. 게이트웨이의 목적이 여러 모델을 중계하는 것이므로
  가용 모델 수가 직접적인 기능 차이가 된다.

**리전 분리(컴퓨트는 서울, Bedrock 은 us-east-1)** — 검토했으나 기본값으로는
채택하지 않았다.

- Bedrock 호출이 리전 간 이동이 되어 요청당 지연이 늘어난다.
- 데이터 전송 비용이 토큰량에 비례해 발생한다.
- 다만 이 구성이 필요한 경우가 있어 `LLMGW_BEDROCK_REGION` 파라미터로 가능하게
  열어 두었다. 예: 데이터 저장은 국내에 두고 모델은 미국 리전을 쓰는 경우.

### 결과

- ECR 푸시가 같은 리전 내에서 끝난다.
- 가장 넓은 모델 선택지를 얻는다.
- **서울 리전 사용자에게는 지연이 늘어난다.** 한국에서 `us-east-1` 왕복은 약
  180ms 다. LLM 응답이 수 초인 워크로드라 상대적 비중은 작지만 0은 아니다.
- 데이터 주권 요건이 있으면 이 기본값을 쓸 수 없다. `--region ap-northeast-2` 로
  배포하고 해당 리전의 모델 가용성을 먼저 확인해야 한다.

---

## 결정 2: 분산 트레이싱(X-Ray / ADOT)을 v1 에서 제외한다

### 배경

조직 기본 방침은 X-Ray 트레이싱을 활성화하는 것이다. ECS 에서 이를 구현하는
방법은 두 가지다.

1. **X-Ray 데몬 사이드카 + `aws-xray-sdk`.** 그런데 `aws-xray-sdk-python` 에는
   FastAPI/Starlette 용 공식 미들웨어가 없다. Django, Flask, aiohttp 만 제공된다.
   직접 미들웨어를 작성해 세그먼트 수명을 관리해야 하고, 스트리밍 응답에서
   세그먼트를 언제 닫을지 판단하는 부분이 특히 까다롭다.
2. **ADOT 컬렉터 사이드카 + OpenTelemetry 자동 계측.** AWS 권장 경로다. 컨테이너
   하나가 추가되고 의존성 4~5개(`opentelemetry-distro`, `-exporter-otlp`,
   `-instrumentation-fastapi`, `-instrumentation-botocore`)가 붙는다.

### 결정

v1 에서는 분산 트레이싱을 넣지 않는다. 대신 다음으로 관측성을 확보한다.

- **상관관계 ID.** 모든 로그 줄에 `correlation_id` 가 붙는다. 클라이언트가
  `X-Request-Id` 를 보내면 그 값을 쓰고, 없으면 생성한다. 같은 값이 사용량
  레코드의 `request_id` 이기도 해서, 로그에서 특정 요청의 집계 반영 여부까지
  추적할 수 있다.
- **EMF 커스텀 메트릭.** 모델별 요청 수, 에러 수, 토큰 수, 비용, 지연을
  CloudWatch 에 올린다. 지연 백분위(p50/p95/p99)를 CloudWatch 에서 산출할 수 있다.
- **Bedrock 에러 코드 로깅.** 업스트림 실패 시 AWS 에러 코드를 구조화 로그에 남긴다.
- **알람 4개.** 5xx, p99 지연, 비정상 타깃, 사용량 기록 실패.

### 검토한 대안

**ADOT 사이드카를 파라미터로 넣고 기본 비활성** — 검토했으나 탈락.

기본이 꺼진 코드 경로는 테스트되지 않은 코드다. 켰을 때 동작하지 않으면 필요한
순간에 쓸 수 없고, 오히려 "있다고 생각했는데 없는" 상태가 된다. 넣지 않고 명시적
으로 없다고 기록하는 편이 정직하다.

**X-Ray 미들웨어 직접 구현** — 탈락.

스트리밍 응답의 세그먼트 수명 관리에 실패 여지가 크다. 원커맨드 배포의 신뢰성이
1순위인 단계에서 검증되지 않은 계측 코드를 넣는 것은 위험 대비 이득이 적다.

### 결과

**얻는 것**

- 사이드카 컨테이너가 없어 태스크 정의가 단순하고 메모리 여유가 크다.
- 의존성이 5개 적다. 이미지가 작고 취약점 표면이 좁다.
- 첫 배포 실패 지점이 줄어든다.

**잃는 것**

- **요청 하나가 게이트웨이 → Bedrock → DynamoDB 를 거치는 구간별 지연을 분해할 수
  없다.** 전체 지연은 알지만 어디서 시간을 쓰는지 모른다. 지연 문제를 진단할 때
  로그 타임스탬프를 대조해야 한다.
- 서비스 맵과 트레이스 뷰가 없다.

**새로 생기는 운영 부담**

지연 원인 분석이 필요할 때 수동 작업이 늘어난다. 완화책으로 사용량 레코드에
게이트웨이 관점 `latency_ms` 를 남기고, Bedrock 에러 코드를 로그에 남긴다.

### 도입 절차 (필요해지면)

1. `requirements.txt` 에 추가:
   `opentelemetry-distro`, `opentelemetry-exporter-otlp`,
   `opentelemetry-instrumentation-fastapi`, `opentelemetry-instrumentation-botocore`
2. `infra/app.yaml` 태스크 정의에 ADOT 컬렉터 사이드카 추가
   (`public.ecr.aws/aws-observability/aws-otel-collector`)
3. 태스크 역할에 `xray:PutTraceSegments`, `xray:PutTelemetryRecords` 추가
4. 컨테이너 환경변수에 `OTEL_EXPORTER_OTLP_ENDPOINT`,
   `OTEL_SERVICE_NAME`, `OTEL_PROPAGATORS=xray` 설정
5. `Dockerfile` CMD 를 `opentelemetry-instrument uvicorn ...` 으로 변경
6. **스트리밍 응답에서 세그먼트가 정상 종료되는지 반드시 확인한다.** 이 지점이
   가장 깨지기 쉽다.

### 재검토 조건

- p99 지연 알람이 반복 발생하고 원인이 로그로 특정되지 않는 경우
- Bedrock 호출과 DynamoDB 호출 중 어느 쪽이 병목인지 판단이 필요한 경우
- 게이트웨이 앞뒤로 다른 서비스가 붙어 호출 체인이 길어진 경우
