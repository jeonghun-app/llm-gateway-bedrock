# 0002. 데이터 저장소로 DynamoDB 를 쓰고 사용량 기록을 단일 트랜잭션으로 처리한다

- 상태: 승인
- 날짜: 2026-08-24

## 배경

저장해야 하는 것은 두 종류다.

**메타데이터** — 계정, 팀, 사용자, API 키. 수량은 조직 규모(수백~수천)이고 거의
변하지 않는다. 접근 패턴은 키 해시로 단건 조회, 계정별 목록 조회다.

**사용량** — 요청 하나당 1건. 조회는 대시보드가 하고, 필요한 것은 계정 / 팀 /
사용자 / 모델 / 키 축의 기간별 합계다.

추가 제약이 두 가지 있었다.

1. **"AWS 자격증명만 있으면 설치가 끝나야 한다."** 스키마 마이그레이션 도구나
   DB 초기화 절차가 필요하면 이 목표가 깨진다.
2. **재시도 안전성.** 클라이언트가 타임아웃 후 재시도하면 같은 요청이 두 번
   집계되어 비용이 부풀려진다. 게이트웨이가 청구 근거를 제공하므로 이건 정확성
   문제다.

## 결정

**DynamoDB 온디맨드** 테이블 3개를 쓴다.

| 테이블 | 용도 |
|---|---|
| `registry` | 계정·팀·사용자·API 키 (단일 테이블 + GSI 1개) |
| `usage` | 요청 단위 원본. `pk=<계정>#<날짜>`, `sk=<request_id>`, TTL 90일 |
| `usage-agg` | 사전 집계 카운터. 원자적 `ADD` 로 누적 |

그리고 **원본 쓰기와 집계 갱신을 하나의 `TransactWriteItems` 로 묶는다.** 원본
Put 에 `attribute_not_exists(sk)` 조건을 걸고, `sk` 를 `request_id` 로 둔다.

## 검토한 대안

### Aurora Serverless v2 (PostgreSQL) — 탈락

조직 기본 RDB 선택지이므로 먼저 검토했다.

- **유휴 비용.** 최소 용량이 0.5 ACU 이고 시간당 과금이라 월 약 $43 다. 요청이
  없어도 발생한다. DynamoDB 온디맨드는 유휴 시 거의 $0 다.
- **설치 목표와 충돌.** VPC 배치, 서브넷 그룹, 파라미터 그룹, Secrets Manager
  로테이션, 그리고 **스키마 마이그레이션**이 필요하다. "자격증명만 넣으면 설치"
  라는 목표를 지키려면 마이그레이션 실행 단계를 배포 스크립트에 넣어야 하고,
  실패 시 부분 적용 상태를 다루는 복잡도가 생긴다.
- **접근 패턴이 관계형을 요구하지 않는다.** 조인이 필요한 질의가 없다. 전부 키
  조회와 카운터 누적이다.
- **커넥션 관리.** Fargate 태스크가 늘면 커넥션 풀 관리나 RDS Proxy 가 필요하다.

Aurora 가 유리했을 조건: 임의 축 조합의 애드혹 분석이 필요하거나, 트랜잭션
경계가 여러 테이블에 걸쳐 복잡한 경우.

### DocumentDB — 탈락

Aurora 와 같은 유휴 비용 문제에 더해, 이 워크로드에 문서 모델의 이점이 없다.

### Timestream (사용량 전용) — 탈락

시계열 집계에는 적합하지만 메타데이터용 저장소를 별도로 둬야 하고, 원본과 집계를
한 트랜잭션으로 묶을 수 없어 멱등성 보장 방식을 따로 만들어야 한다.

### 집계를 두지 않고 원본만 스캔 — 탈락

대시보드 조회마다 기간 내 모든 원본을 읽으면 요청 수에 비례해 조회 비용과 지연이
늘어난다. 30일 · 10만 요청이면 매 조회가 10만 항목 읽기가 된다.

### 집계를 개별 `UpdateItem` 10회로 처리 — 탈락

- 왕복이 10회라 요청당 50ms 이상 추가된다.
- 부분 실패 시 일부 축만 반영된 상태가 남는다.
- 원본 쓰기와 원자적으로 묶을 수 없어 멱등성 보장이 애플리케이션 로직에 의존한다.

### 집계를 DynamoDB Streams + Lambda 로 비동기 처리 — 보류

원본 쓰기만 동기로 하고 집계는 스트림 컨슈머가 처리하는 방식이다. 요청 경로가
가벼워지는 장점이 있지만,

- 대시보드에 반영이 수 초 지연된다. 예산 강제에 이번 달 누적치가 필요하므로
  지연이 곧 예산 초과 허용 폭이 된다.
- Lambda, 스트림, DLQ, 재처리 절차가 추가된다. 구성 요소가 늘어 "한 번에 설치"
  목표와 멀어진다.

트래픽이 커져 요청 경로 지연이 문제가 되면 이 방식으로 전환한다.

## 결과

**얻는 것**

- 유휴 비용이 사실상 없다. 데모·검증 환경을 켜 둬도 부담이 없다.
- **재전송 안전성이 저장소 제약으로 보장된다.** 애플리케이션 로직의 정확성에
  의존하지 않는다. 정렬 키는 서버가 만드는 `usage_id` 이고 같은 값을
  `ClientRequestToken` 으로 넘기므로, 네트워크 재전송으로 같은 트랜잭션이 두 번
  도착해도 집계가 두 번 더해질 경로가 없다. 반대로 클라이언트가 지정하는
  `X-Request-Id` 는 키로 쓰지 않는다. 그것을 키로 쓰면 헤더를 고정하는 것만으로
  집계와 월 예산을 우회할 수 있다.
- 요청당 왕복이 1회다. 11개 항목을 한 번에 쓴다.
- 대시보드 조회 비용이 요청 수와 무관하다. 30일 조회는 파티션 30개 읽기다.
- 스키마 마이그레이션이 없다. 테이블은 CloudFormation 이 만들고 끝이다.
- 예산 검사가 단일 `BatchGetItem` 이다. 월 집계 행 4개만 읽는다.

**잃는 것**

- **쓰기 비용이 2배다.** 트랜잭션 쓰기는 일반 쓰기의 2배 용량을 소비한다. 요청당
  약 22 WRU 이고, 100만 요청이면 약 $27 다. 개별 쓰기면 약 $14 였다. 멱등성과
  1회 왕복의 대가로 받아들였다.
- **애드혹 분석이 어렵다.** 미리 정한 5개 축(전체/팀/사용자/모델/키) 외의 조합은
  집계되지 않는다. 예를 들어 "팀 A 의 사용자별 모델 분포" 는 원본을 읽어야 한다.
  축을 추가하면 요청당 쓰기가 늘어난다.
- **최대·백분위 지연을 집계에 담을 수 없다.** `ADD` 로는 최댓값을 누적할 수 없다.
  평균만 DynamoDB 에 두고 백분위는 CloudWatch EMF 메트릭에서 본다.
- **한 계정의 쓰기 처리량에 상한이 있다.** 집계 파티션이 `계정#기간` 이라 파티션당
  1,000 WCU 제약을 받는다. 한 계정이 초당 수백 요청을 넘으면 파티션 분할(샤드
  접미어 + 조회 시 합산)이 필요하다.

**새로 생기는 운영 부담**

- 축을 추가하려면 코드 변경과 함께 요청당 쓰기 비용 증가를 감안해야 한다.
- 과거 데이터 재집계 도구가 없다. 집계 로직 버그를 고쳐도 이미 쌓인 값은 그대로다.
  원본이 TTL 안에 있으면 재집계 스크립트를 만들 수 있지만 현재는 없다.

**비용 영향**

- 유휴: 거의 $0 (PITR 저장 비용만)
- 100만 요청: 쓰기 약 $27 + 읽기·저장 소액
- Aurora Serverless v2 대비 유휴 시 월 약 $43 절감

## 구현상 주의점

기록해 둘 함정이 두 개 있었다.

1. **`boto3` 리소스의 `meta.client` 를 트랜잭션에 쓰면 안 된다.** 리소스를 만들 때
   그 클라이언트에 문서 변환 핸들러가 등록되어, 이미 AttributeValue 로 직렬화한
   파라미터가 한 번 더 변환되면서 호출이 깨진다. `boto3.client("dynamodb")` 로
   별도 저수준 클라이언트를 만들어 쓴다.
2. **`Decimal` 의 지수 표기를 저장하면 안 된다.** `Decimal("0").quantize(...)` 는
   `Decimal('0E-10')` 이 되고 문자열로는 `"0E-10"` 이다. DynamoDB 는 이 표기를
   숫자로 받지 않아 트랜잭션 전체가 실패한다. 직렬화 직전에 항상 고정소수점
   표기로 변환한다. 두 지점(`pricing.calculate` 와 `repository._serialize`)에서
   막았고 회귀 테스트가 있다.

## 재검토 조건

- 한 계정의 초당 요청이 수백 건을 넘으면 집계 파티션 분할이 필요하다.
- 애드혹 분석 요구가 반복되면 원본을 S3 로 내보내 Athena 로 질의하는 경로를
  추가한다. 집계 축을 늘리는 것보다 비용 효율이 좋다.
- 요청 경로 지연이 문제가 되면 DynamoDB Streams 기반 비동기 집계로 전환한다.
