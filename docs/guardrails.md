# 가드레일

Amazon Bedrock Guardrails 를 게이트웨이가 모든 요청에 붙여 준다. 계정 단위
기준선을 정하고, 팀·사용자 단위로 면제할 수 있다.

## 왜 게이트웨이가 하는가

고객이 AWS 콘솔에서 가드레일을 만들어도 **그것만으로는 적용되지 않는다.**
Converse 호출마다 `guardrailConfig` 에 식별자를 실어야 한다. 즉 애플리케이션이
그 필드를 빼면 통제가 조용히 사라진다.

게이트웨이가 중앙에서 붙이면:

- 클라이언트가 가드레일을 빼거나 다른 것으로 바꿀 수 없다
- 계정·팀·사용자 식별자와 정책이 연결된다
- 버전을 고정하고 한곳에서 교체한다
- 개입을 기존 사용량 축(계정/팀/사용자/모델/키)에 귀속시킨다
- 면제에 사유를 남기고 권한을 제한한다

## 설정

### 1. 계정 기준선

```bash
curl -X PUT "$GATEWAY_URL/admin/accounts/acme/guardrail" \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"guardrail_id":"abc123xyz","guardrail_version":"2"}'
```

저장 전에 게이트웨이가 `GetGuardrail` 로 **그 가드레일이 실제로 있고 `READY`
상태인지 확인한다.** 없는 가드레일을 저장하면 이후 모든 요청이
`ValidationException` 으로 실패하는데, 그것을 배포 후에 알게 되는 것보다 여기서
막는 편이 낫다.

**버전은 숫자만 받는다.** `DRAFT` 는 거부된다. 실측 결과 `DRAFT` 도 런타임에서
동작하기 때문에, 막지 않으면 내용이 예고 없이 바뀌는 정책을 강제하게 된다.

조회와 해제:

```bash
curl "$GATEWAY_URL/admin/accounts/acme/guardrail" -H "X-Admin-Token: $ADMIN_TOKEN"
curl -X DELETE "$GATEWAY_URL/admin/accounts/acme/guardrail" -H "X-Admin-Token: $ADMIN_TOKEN"
```

`enabled: false` 로 두거나 삭제하면 그 계정 전체가 가드레일 없이 동작한다. 둘 다
플랫폼 관리자만 할 수 있다.

### 2. 면제

```bash
curl -X PUT "$GATEWAY_URL/admin/accounts/acme/users/alice/guardrail-exemption" \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"exempt":true,"reason":"레드팀 평가 2026-Q3 (TICKET-1234)"}'
```

팀 단위도 같다 (`/teams/{team_id}/guardrail-exemption`).

**사유가 필수다.** 왜 통제를 껐는지 남지 않으면 나중에 검토할 수 없다. 해제할
때는 사유가 필요 없고, 저장된 사유도 지워진다.

## 우선순위

```
사용자 면제  →  팀 면제  →  계정 기준선
```

사용자 면제가 팀 면제보다 구체적이라 먼저 본다. 계정 기준선이 없거나 꺼져
있으면 아무것도 적용되지 않는다.

**계층별로 다른 가드레일을 고르는 기능은 없다.** 가드레일 ID 사이에는 강도의
전순서가 없어서 "더 엄격한 것이 이긴다" 같은 규칙을 정의할 수 없다. 한 정책은
개인정보에 강하고 다른 정책은 폭력 표현에 강할 수 있고, Converse 는 호출당 설정
하나만 받는다. 그래서 하위 계층은 **면제만** 할 수 있다.

## 권한 — 통제를 끄는 경로를 제한한다

| 작업 | 필요 권한 |
|---|---|
| 기준선 조회 | 계정 관리자 |
| 기준선 설정·갱신 | 계정 관리자 |
| **기준선 삭제** | **플랫폼 관리자** |
| **팀·사용자 면제** | **플랫폼 관리자** |

계정 관리자가 자기 계정의 안전 통제를 스스로 해제할 수 있으면 통제라고 부를 수
없다. 셀프서비스 경로(`/auth/keys`)에는 가드레일 관련 엔드포인트가 없다.

면제 변경은 `WARNING` 수준으로 로그에 남고 행위자(`actor`)가 함께 기록된다.
공유 관리 토큰을 쓰면 행위자가 고정 문자열이라 사람을 식별할 수 없다. 개인 추적이
필요하면 OIDC 를 관리 경로로 쓴다.

## 스트리밍 — `sync` 를 강제한다

가드레일이 붙은 스트리밍 요청은 `streamProcessingMode` 를 `sync` 로 고정한다.
클라이언트가 이 값을 고를 수 없다.

sandbox 가드레일로 실측한 결과다.

| 모드 | 첫 청크 | 청크 수 | 클라이언트가 받은 내용 |
|---|---|---|---|
| `sync` | 1.42s | 1 | 차단 메시지만 |
| `async` | 0.76s | 7 | **차단 대상 단어가 그대로 전달됨** |

`async` 는 생성된 텍스트를 먼저 보내고 **나중에** 개입을 알린다. 지연 0.66초를
아끼는 대가로 통제가 무의미해진다.

이 점이 게이트웨이 내부의 응답 필터와 다르다. 내부 필터로는 이미 보낸 청크를
회수할 수 없어 스트리밍을 지원할 수 없지만, Bedrock 은 서버 측에서 버퍼링하므로
`sync` 로 안전하게 스트리밍할 수 있다.

## `trace` 는 끈다

`guardrailConfig.trace` 를 항상 `disabled` 로 보낸다.

켜면 응답의 `trace.guardrail` 에 **`modelOutput`(차단하려던 응답 원문)** 이
들어온다. 그것을 로그에 남기면 막으려던 내용이 로그로 샌다. 탐지된 개인정보와
정규식 일치 내용도 assessment 에 담긴다.

그래서 개입 여부는 응답 본문이 아니라 **`stopReason`** 으로만 판별한다. 차단된
내용이 게이트웨이 쪽에 남지 않는다.

## 개입했을 때

Bedrock 이 **200 과 차단 메시지**를 반환한다. 게이트웨이도 200 을 유지하고
`finish_reason` 을 `content_filter` 로 준다. 4xx 로 바꾸지 않는다 — 가드레일
검사와 (출력 단계라면) 모델 생성 비용이 이미 발생했다.

사용량 레코드에 세 필드가 남는다.

| 필드 | 의미 |
|---|---|
| `guardrail_applied` | 가드레일을 붙여 호출했는가 |
| `guardrail_intervened` | 가드레일이 개입해 차단했는가 |
| `guardrail_exempt_scope` | 면제된 계층(`team`/`user`). 면제가 아니면 빈 값 |

"적용했는데 개입하지 않았다" 와 "적용조차 하지 않았다" 는 완전히 다른 상태라
나눠 기록한다.

## 잘못된 구성

실측으로 확인한 AWS 동작이다.

| 상황 | 결과 |
|---|---|
| 존재하지 않는 ID | `ValidationException` — 호출 실패 |
| 없는 버전 | `ValidationException` |
| 다른 계정 ARN | `ValidationException` |
| `DRAFT` 버전 | 정상 동작 (그래서 저장 시 거부한다) |

**조용히 검사를 건너뛰는 경우는 없다.** AWS 자체가 fail-closed 다. 따라서
게이트웨이는 가드레일 없이 재시도하지 않는다. 그것이 이 기능에서 가장 위험한
구현 실수다.

저장 시 검증은 런타임 안전을 대체하지 않는다. 저장 시점에 유효했던 가드레일이
나중에 삭제되거나 권한이 바뀔 수 있고, 그때는 AWS 가 요청을 거부한다.

## IAM

런타임에 `guardrailConfig` 를 붙이는 것은 **기존 `bedrock:InvokeModel` 권한으로
충분하다.** 태스크 역할과 동일한 권한만 가진 역할을 만들어 실측했다.
`bedrock:ApplyGuardrail` 은 필요하지 않다.

저장 시 검증을 위해 `bedrock:GetGuardrail` 을 태스크 역할에 추가했다.

## 비용

**가드레일 사용료는 사용량 집계에 포함되지 않는다.** Converse 응답의
`TokenUsage` 에 가드레일 사용량 필드가 없어서 계산할 수 없다.

즉 대시보드의 비용은 **모델 토큰 비용만**이다. 가드레일을 켜면 AWS 청구서가
대시보드보다 크다. 모르는 비용을 0 으로 더하면 단가 미등록 모델과 같은 예산
우회가 생기므로, 더하지 않고 이 문서에 적는다.

개입 단계에 따라 모델 비용이 갈린다(실측).

| 개입 단계 | `usage` | 모델 비용 |
|---|---|---|
| 입력 | `{0, 0, 0}` | 없음 — 모델이 생성하지 않았다 |
| 출력 | 실제 토큰 수 | **발생** — 모델이 이미 생성했다 |

## 아직 없는 것

- **면제 만료.** 지금은 사유만 남고 만료가 없다. 임시 예외가 영구 예외가 되는
  것을 시스템이 막지 않는다. 운영 절차로 관리해야 한다.
- **승인자 기록.** 요청자와 승인자를 구분하는 2인 승인이 없다.
- **계층별 다른 가드레일.** 위에 적은 이유로 넣지 않았다.
- **가드레일 비용 집계.** AWS 가 응답으로 주지 않는 한 불가능하다.
- **대시보드 노출.** 사용량 레코드에는 남지만 화면에는 아직 없다.
